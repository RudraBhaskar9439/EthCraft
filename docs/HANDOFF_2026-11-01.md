## Connect and use it

Last checked public Minecraft address: **`159.223.110.159:51967`**. Current client route includes Minecraft Java **26.3**. Last checked onboarding origin: **`https://distributors-formerly-encounter-specific.trycloudflare.com`**. The tunnel URL/address can change; obtain fresh values using the host status command below. Do not reuse an old challenge URL or post it publicly.

1. In the AgentCity Discord server, run `/start` and finish the fresh private setup link. Existing wallet owners sign into their existing Privy account before linking Discord.
2. New users reserve an unused Minecraft name with `/profile name:<unused-name> login:local`. **Ruddy2 is already registered**; its owner should keep that account. `Ruddy` is a separate existing identity, not a case-based alias to adopt. Microsoft login is currently refused until real provider/server verification exists.
3. Connect Minecraft using the reserved name. Run Discord `/join` and approve only the connection just initiated. A new connection can require new approval.
4. Enter `/play`. Open `/agents` in Discord, create an agent if a slot is free, and use the linked private room's controls. In-game `/agent create` is also available. Keep wallet/account setup in Discord.
5. Inspect supplies and the assigned work area before requesting a build. The source chest, destination chest and build origin are the agent's registered coordinates, not arbitrary nearby chests.

Fresh account setup does not automatically fund a wallet. On-chain funding, custody and purchases use separate reviewed confirmations. A no-popup managed wallet still produces a cryptographic signature through its provider.

### Example: list and buy one stick

Seller: carry a real stick, then Discord `/assets action:register_item source:player count:1`, confirm, wait for confirmed custody/mint, get its ID with `action:owned`, then `action:list asset:<id> price:4` and confirm. Registering one from three leaves two with the seller. Plain resource lots support oak planks, cobblestone, stone, dirt, sand, oak logs, sticks and stone bricks, **1–64 items per NFT**. Equipment is **one exact item**, retaining damage, enchantments, name, lore and native metadata. Containers, bundles and nested inventories are excluded. No partial fills.

Buyer: browse, preview and confirm the 4 CITY purchase. If short of CITY, separately confirm a GEM/CITY swap first. CITY and NFT ownership transfer atomically in the marketplace. Redeem the purchased item NFT, then collect with `/bazaar claim` on the approved game connection. Keep the original operation ID through any uncertain result.

Two old backed one-stick listings priced in the retired currency were retained at cutover. They have withdrawal-only cards. Cancel/claim those first, then separately register the returned stick and choose a CITY price. No automatic conversion, replacement mint or assumed owner approval occurs.

### Example: land and a house

Catalog parcels are 16×16 in `agentcity_estates`: IDs 1/2/3/4 start at `(0,0)`, `(32,0)`, `(0,32)`, `(32,32)` in x/z; terrain is normal, not automatically flattened or furnished. Public gaps remain outside parcels.

WorldGuard/native checks apply the confirmed owner and their bound agents; strangers are denied. Ownership refresh runs every 10 seconds with a 30-second freshness limit and fails closed. ## AI: what it can actually do now

The active personal-agent settings select local Ollama **`qwen3:4b`**. [intent-planner.mjs](../backend/src/playable/intent-planner.mjs) sends text/JSON at temperature 0, with an 8,192-token context setting, up to 4,096 generated tokens and a 120-second request timeout. Input is capped at 500 characters; a workflow has at most six steps. This is a real language-model planner, not just a fixed command template. Generated actions still have to pass strict schemas, permission checks and native material accounting.

The separate historical inference provider defaults to `qwen3:1.7b`; that does **not** identify the currently configured personal-agent model. 0G has not replaced Ollama yet.

| Tool family | Current capability and boundary |
| --- | --- |
| Conversation/control | Clarify requests, report progress, follow/come/wait, pause/resume, inspect supplies/capabilities, request a screenshot |
| Construction | Parameterized house/tower/bridge/wall/stair/arch, platform/shelter and bounded relative custom geometry. Custom layouts: up to 256 blocks, 8×8 footprint and six layers, subject to actual plot bounds/access strips |
| Build materials | Full blocks: oak planks, cobblestone, stone, stone bricks, dirt, glass, bricks and oak logs. Full-block stairs are not oriented stair items/furniture |
| Gathering | Observed oak logs/planks, dirt and sand in the owner's registered plot, at most 16 blocks per task; actual drops required |
| Crafting | One oak log → four planks; two planks → four sticks; four stone → four stone bricks. Desired output counts use whole batches, so leftovers can remain |
| Collection/delivery | Actual stock from/to registered owner source/destination chests, bounded quantities; no general delivery to arbitrary players/locations |
| Screenshots | Private rendered view of the bot's actually loaded bounded block cache, with observation metadata; not the Minecraft client's framebuffer |
| Financial assistance | In-game model can propose supported registration/swap previews and read wallet balances; it cannot approve them. Discord remote agent planning currently excludes market/swap/wallet actions; use explicit `/assets` commands |

Example supported requests:

```text
Inspect my supplies and work area.
Build a 4 by 4 oak-plank house, four blocks high.
Gather two oak planks, craft four sticks, and deliver four sticks to my destination chest.
What is the update? Share a screenshot.
Stop. / Resume.
```

Carried building materials are used first, then the registered source chest. Native withdrawals and placements are journaled; already-correct blocks are not charged again. Obstructions, unknown effects, unsafe paths and missing stock pause execution. Existing builds, foundations, access strips and chests are protected. A completed geometry check alone does not prove a custom design matches the user's meaning: free-form geometry remains experimental.

Direct in-game tasks require initial nearby owner authority and the owner to remain online, though they may move elsewhere after acceptance. Discord can instead grant scoped physical execution while the human is offline. That grant names owner, agent, plot, tools and expiry; the receiving boundary checks it. One unfinished physical task per owner is retained. A different task cannot silently replace an immutable workflow with effects. Pause/resume or reconcile it; **Cancel task** only abandons a quiescent task without effects/pending operations/carried items.

The pool provides CITY/GEM exchange; price moves with actual pool swaps and liquidity. Sellers set their asset's CITY price separately. There is no gameplay-activity demand oracle, automatic supply controller or dynamic fee algorithm. Buying an asset with existing CITY need not use the swap pool.

The hook's `beforeSwap` checks the intended pool and an authorized healthy, unexpired StateRegistry report. The publisher checks current ownership synchronization, native escrow readiness and the estate catalog. Reports last 240 seconds and refresh when at most 120 remain; the contract maximum is 300 seconds. This trusts the publisher and tolerates report staleness until expiry. The hook does not directly inspect Minecraft blocks, enforce house entry or gate every marketplace purchase. Registry/market contracts enforce asset settlement; native permissions enforce game access.
